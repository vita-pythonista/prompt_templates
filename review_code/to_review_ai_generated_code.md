Порядок работы
Сначала, до чтения кода, сформулируй ожидаемое поведение по требованиям: что должно происходить при нормальном вводе, пустом вводе, некорректном вводе и при отказе внешних систем.
Затем пройди по коду и проверь каждую категорию ниже. Для каждой категории выполни перечисленные проверки, а не общий просмотр.
Для каждого найденного дефекта придумай конкретный вход или ситуацию, при которой код ведёт себя неправильно. Если такой сценарий придумать не удаётся - это не дефект, не включай его.
Категории и проверки

1. Игнорирование контекста проекта (дублирование)

Для каждой вспомогательной функции, подключения к БД, клиента, форматтера, валидатора: нет ли аналога в контексте этого проекта или в импортах этого же файла?
Соблюдены ли соглашения проекта (общие подключения, логирование, конфигурация)?

2. Производительность и конкурентность

Запросы к БД или сети внутри цикла (N+1).
Чтение целиком в память того, что может быть большим (вся таблица, весь файл, весь ответ API).
Последовательность «прочитать - проверить - записать» без блокировки или атомарной операции (race condition).

3. Врущие комментарии

Разбери каждый докстринг и комментарий на отдельные утверждения («фильтрует по статусу», «сортирует», «бросает ValueError», «валидирует»).
Для каждого утверждения найди строку кода, которая его выполняет. Нет такой строки - дефект.

4. Безопасность

Любая подстановка значения в текст SQL, shell-команды, пути к файлу или HTML через f-строку, .format, % или конкатенацию. Отдельно проверь ORDER BY, имена таблиц и колонок: их нельзя параметризовать, нужен белый список.
Пароли, токены, ключи, строки подключения в коде.
Внешний ввод без проверки типа, диапазона и допустимых значений. Доступ к чужим данным по id из запроса (IDOR).
Небезопасные генераторы (random для токенов), отключённая проверка TLS, слабые хэши для секретов.

5. Проглатывание ошибок

Каждый except / catch: какие исключения ловятся (широкий Exception - подозрительно), что происходит дальше.
Возврат значения по умолчанию ([], {}, 0, None, "") вместо исключения. Можно ли отличить его от настоящего результата?
Кто и как узнает об ошибке: есть ли лог, проброс, ответ с ошибкой?

6. Тесты-тавтологии

Что замокано? Если замокана сама проверяемая функция или ключевая логика - тест ничего не проверяет.
Как вычислено ожидаемое значение? Если той же формулой, что и в коде, - тест повторяет ошибку.
Насколько сильны проверки? is not None, assert result, called_once без проверки аргументов - слабые.
Мысленно сломай код (замени >= на >, удали фильтр, верни []). Упадёт ли тест? Если нет - дефект.

7. Галлюцинации API и пакетов

Для каждого импорта и каждого вызова внешней библиотеки: существует ли такой модуль, функция, метод и параметр в указанной версии?
Не будь уверен там, где не уверен. Если сомневаешься, пометь находку «требует проверки» и дай команду для проверки (python -c "from X import Y", ссылка на раздел документации).
Новые пакеты в зависимостях: правдоподобное, но незнакомое имя - риск slopsquatting. Пометь для проверки на PyPI / npm (возраст, мейнтейнеры, загрузки).

Если находишь дефект вне этих категорий (граничные случаи, таймзоны, off-by-one, неверное понимание требований), включи его с категорией «Прочее».

Правила, чтобы ревью само не стало правдоподобным, но неверным
Каждая находка привязана к конкретной строке, и ты цитируешь эту строку дословно.
Не придумывай дефекты ради количества. Пять настоящих находок лучше десяти, из которых половина спорные.
Не выдавай стилистические замечания за дефекты. Их можно перечислить одной строкой в конце.
Отмечай уверенность: «точно» - дефект виден из кода; «требует проверки» - зависит от того, чего ты не видишь (версия библиотеки, схема БД, код вне фрагмента).
Не переписывай код. Исправления показывай короткими фрагментами внутри комментариев.
